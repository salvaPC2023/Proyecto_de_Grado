# Implementation Plan: LLM Description Standardization Module

**Branch**: `003-llm-description-standardization` | **Date**: 2026-06-12 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/003-llm-description-standardization/spec.md`

## Summary

The LLM Description Standardization module extends the PM01 closure flow from Feature 002
with an optional AI-assisted text normalization step. When a Technician taps "Standardize
description" in the closure form, the mobile app calls a new backend endpoint that forwards
the free-text description to the Anthropic Claude API (via a hexagonal outbound adapter) and
returns a structured, normalized Spanish-language version. The Technician reviews, optionally
edits, and confirms the result — only the confirmed text is stored in the existing
`work_description` field. No schema changes are required. If the AI service is unavailable
(timeout, quota, offline), a non-blocking fallback preserves the original text and the closure
submission path is never blocked.

## Technical Context

**Language/Version**: Python 3.11 (backend), Dart 3.x / Flutter 3.x (mobile)

**Primary Dependencies**:
- Backend: FastAPI 0.111+ (existing), `anthropic` Python SDK for LLM calls
- Mobile: Riverpod 2.x (AsyncNotifier), Dio 5.x (existing), `connectivity_plus`
  (existing — already used in Feature 002 offline queue)

**Storage**: No new tables or columns. The existing `work_description` VARCHAR column in the
`ot_steps_closures` table (Feature 002) stores the final confirmed text as-is. No migration
required.

**Testing**:
- Backend: pytest + httpx; mock the `anthropic` SDK response in unit tests
- Mobile: flutter_test; mock `StandardizationRepository` in notifier unit tests

**Target Platform**: Railway Linux server (FastAPI); iOS 14+ / Android 8+

**Project Type**: mobile-app + REST API extension (no new project; adds to Feature 002 structure)

**Performance Goals**:
- Total round-trip (mobile tap → backend → Anthropic → backend → mobile render): ≤ 10 s (SC-001)
- Backend timeout on the Anthropic SDK call: 8 s (leaving 2 s for network and FastAPI overhead)

**Constraints**:
- Anthropic API key stored as Railway environment variable (`ANTHROPIC_API_KEY`); never sent to
  the mobile client
- Free-tier usage — `claude-haiku-4-5` model for cost and latency efficiency; occasional
  quota errors are expected and handled as graceful fallback
- Hexagonal: `anthropic` SDK imported only inside the outbound adapter; domain and use-case
  code depend solely on the `StandardizationServicePort` interface
- Online-only feature: the standardization button is hidden or disabled when `connectivity_plus`
  reports no connectivity
- No automatic retries on the backend; user-triggered retry via mobile "Retry" button

**Scale/Scope**: 1 Supervisor (reads results), up to 200 Technicians (trigger standardization);
stateless — no conversation history or per-user context sent to the LLM

**Structure Decision**: Mobile + API (extends existing monorepo). No new top-level directories.
Backend adds one new router (`descriptions.py`) and one new outbound adapter
(`anthropic_adapter.py`) inside the existing hexagonal structure. Mobile adds one new
repository, one new Riverpod notifier, and one new widget that is embedded in the existing
PM01 closure form screen from Feature 002. This feature establishes the `StandardizationServicePort`
that would also serve future LLM features (e.g., feature communications module).
