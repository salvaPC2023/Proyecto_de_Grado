# Implementation Plan: OT Management Module

**Branch**: `002-ot-management` | **Date**: 2026-06-08 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-ot-management/spec.md`

## Summary

The OT Management module implements the full lifecycle of Work Orders (Órdenes de
Trabajo) in a mobile maintenance app. Supervisors create OTs with a mandatory step list
(3 fixed PMNN safety steps + custom PMNN/PM01 steps) and assign them to Technicians by
shift. Technicians register PM01 step closures (actual duration, deviation key,
description, safety question) with offline queuing via Drift/SQLite. An OT transitions
from Released → Notified once all PM01 steps carry valid closures and the backend
confirms the `Notif. final` + `Sin ttbjo. real` flags. Supervisors monitor their shift's
OTs in real time, access a technical location report ranked by OT count, and view a
per-technician workload summary showing each technician's OT count for the active shift
with drill-down to their specific OTs (read-only).

## Technical Context

**Language/Version**: Python 3.11 (backend), Dart 3.x / Flutter 3.x (mobile)

**Primary Dependencies**:
- Backend: FastAPI 0.111+, SQLAlchemy 2.0 (async), Alembic, pydantic-settings,
  python-jose (JWT validation)
- Mobile: Riverpod 2.x (AsyncNotifier), Drift 2.x (SQLite ORM), Dio 5.x (HTTP),
  go_router 13.x, connectivity_plus 6.x

**Storage**:
- Remote: PostgreSQL 15 (Railway) — canonical source of truth
- Local (mobile): SQLite via Drift — offline closure queue + OT list cache

**Testing**:
- Backend: pytest + httpx (async test client), pytest-asyncio, factory_boy
- Mobile: flutter_test (unit + widget tests), integration_test package

**Target Platform**: Railway Linux server (FastAPI + PostgreSQL); iOS 14+ / Android 8+

**Project Type**: mobile-app + REST API web-service

**Performance Goals**:
- Technician OT list: < 3 s for up to ~20 OTs per shift
- PM01 closure confirmation (online): < 5 s round-trip
- Offline sync: all queued closures transmitted within 30 s of reconnection

**Constraints**:
- Hexagonal architecture on backend: domain core isolated from FastAPI / SQLAlchemy
- MVVM + Riverpod on Flutter; BLoC/Cubit forbidden
- Repository layer abstracts local Drift and remote FastAPI
- All secrets via environment variables; no hardcoded credentials
- Loading states required for every async call in the mobile UI
- Offline PM01 closures queued in Drift and auto-synced on connectivity restoration

**Scale/Scope**: ~3 shifts/day, up to 200 technicians total, ~20 OTs/technician/shift
